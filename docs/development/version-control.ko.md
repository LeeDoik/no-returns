# 로컬 Git 버전 관리

[English](version-control.en.md)

> **과거 기록 · 2026-09-12 폐기/대체.** 현재 게임은 [PSX 우주 배송 기획](../current/01-overview.ko.md)을 따른다. 아래 구현·실행·아트·수치는 과거 자료이며 현재 상태가 아니다. 삭제된 파일은 경로 기록으로만 남긴다.


> 문서 체계 개정: 이 파일의 버전·수치는 작성 당시 기준입니다. 현재 규칙·미완료 상태는 [문서 홈](../README.md)을 먼저 확인하세요.

2026년 9월 7일. 사용자가 선택한 범위는 **로컬 Git만 사용**입니다. GitHub 저장소와 원격 연결은 만들지 않습니다.

## 기준점

첫 확장 프로토타입 0.5를 첫 커밋으로 기록하고 `v0.5.0` 태그로 표시합니다. 기존 화면의 0.5와 같은 기준 버전이며, 기능 변경이나 새 빌드를 뜻하지 않습니다. 기본 브랜치는 `main`입니다. 과거 0.1~0.4 작업은 별도 커밋이 없었으므로 복원 가능한 Git 이력으로 꾸미지 않습니다. 기존 문서는 개발 과정의 기록으로 보존합니다.

이 기준점에는 화물 네 종류, A/B 목적지, 인원별 목표, 위치 알림, 보너스 근무, 설정 저장, 상자 방향 수정, 직원·상자 충돌, 한·영 문서, 테스트와 빌드 도구가 포함됩니다.

## 기록하는 파일

- 코드·장면·Godot 프로젝트와 내보내기 설정, `.gd.uid` 식별 파일.
- 한국어·영어 문서, 테스트, 실행·빌드 도구, 라이선스 고지.
- `.gitignore`, `.gitattributes`, 프로젝트 작업 규칙.

Godot 캐시 `.godot/`, 내려받은 엔진·템플릿 `.tools/`, 검사 기록 `artifacts/`, 실행 파일·ZIP `build/`, 임시 파일과 로그는 제외합니다. 환경 비밀정보·내보내기 자격증명·개발용 Steam App ID 파일·인증서도 제외합니다. 실행 파일은 Git에 넣지 않고 빌드 도구로 다시 만듭니다. 큰 아트 원본이 필요해지면 Git LFS 도입을 따로 검토합니다.

텍스트는 저장소에서 LF로 통일하고 Windows 실행용 `.cmd`·`.bat` 파일은 작업 폴더에서 CRLF로 유지합니다.

## 앞으로의 작업 방식

1. 기능 추가나 수정 전에 현재 변경을 확인합니다. 작업 브랜치는 `codex/짧은-작업명` 형태를 사용합니다.
2. 관련 코드와 두 언어 문서를 함께 수정합니다.
3. 변경에 맞는 검사를 실행하고 결과를 확인합니다. 전체 게임 검사는 `python tools/run_tests.py`입니다.
4. 변경 내용을 검토하고 한 작업 단위로 커밋합니다. 관련 없는 사용자 변경은 섞지 않습니다.
5. 검증한 작업을 `main`에 반영합니다. 배포 기준점을 만들 때만 새 태그를 붙입니다.

기존 태그는 다른 커밋으로 옮기지 않습니다. 수정 배포는 `v0.5.1`, 다음 기능 묶음은 `v0.6.0`처럼 번호를 올립니다. 태그 번호는 내부 프로토타입 식별 방식이며 상용 출시 약속이 아닙니다.

## 이력 확인과 복구

프로젝트 폴더의 터미널에서 `git status`로 미저장 변경을, `git log --oneline --decorate`로 저장 이력을 봅니다. `git show v0.5.0`은 첫 기준점을 보여줍니다. 커밋은 파일 저장과 별개로 변경 묶음을 기록하는 단계입니다. [Git 공식 설명](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control)

되돌릴 때는 “어느 버전으로 돌아가고 싶은지” 알려주세요. 현재 작업을 보존한 뒤 별도 복구 브랜치나 되돌리기 커밋으로 처리합니다. 로컬 이력은 다른 PC나 클라우드에 백업되지 않으므로 디스크 손상에 대비한 외부 백업은 별도로 필요합니다.

다른 폴더나 PC에서 소스를 복원하면 Godot 엔진을 먼저 준비해야 합니다. `tools/setup_godot.ps1`로 고정한 엔진을 복원할 수 있으며 Windows 내보내기는 [빌드 인계](../steam/07-build-handoff.ko.md)의 대응 템플릿도 필요합니다.
