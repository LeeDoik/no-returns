# NO RETURNS — 온라인·Steam 빌드 준비 계획

[English](04-online-and-build-plan.md)

**상태:** Godot 4.7.2 확장 프로토타입 0.5에 화물 네 종류·인원별 목표·A/B 목적지·위치 알림·추가 근무를 구현했습니다. 로컬 두/네 프로세스 ENet 검사와 Windows 내보내기를 검증했습니다. Steam 통신·실제 App ID·Steam 설치는 미구성입니다. [현재 실행 안내](../prototype/05-expanded.ko.md)와 [빌드 인계](07-build-handoff.ko.md)를 참고하세요.  
**갱신일:** 2026년 9월 7일

## 1. 접속 구조 제안

비공개 Steam 로비로 초대와 참가자를 관리하고, 최신 Steam P2P 통신으로 게임 메시지를 전달합니다. 한 플레이어가 방장이 되어 시뮬레이션과 최종 판정을 맡고 나머지가 접속합니다.

Steam 로비와 통신 계층은 별도 기능입니다. Valve는 소규모 파티에 로비/P2P 구성을 권장하며 최신 통신 API는 Valve 네트워크로 데이터를 중계할 수 있습니다. 이 게임에 맞는 방향으로 판단하되 구현 테스트가 필요합니다. [Steam 멀티플레이](https://partner.steamgames.com/doc/features/multiplayer), [Steam 통신](https://partner.steamgames.com/doc/features/multiplayer/networking)

자체 상시 게임 서버를 운영하지 않는 구조입니다. 모든 부가 서비스나 연동이 무료라거나 장거리 지연이 사라진다는 뜻은 아닙니다. 운영비나 연결성을 약속하기 전에 선택한 방식을 측정합니다.

## 2. Godot 연동 선택

후보는 GodotSteam과 호환되는 Steam 기반 MultiplayerPeer이며, 최신 SteamNetworkingSockets 계열을 사용하는 방식입니다. 지원되는 연동 경로 하나를 선택하고 개발을 늘리기 전에 전체 버전 조합을 고정합니다.

기존 [GodotSteam GitHub 저장소](https://github.com/GodotSteam/GodotSteam)는 현재 개발 작업의 위치를 [Codeberg](https://codeberg.org/godotsteam/godotsteam)로 안내합니다. 이전 사실은 확인했지만, 이번 준비에서 최신 릴리스 호환표까지 검증하지는 못했습니다. 버전 선택 전에 관리자의 최신 릴리스 안내를 읽습니다. [Expresso Bits의 Steam Multiplayer Peer](https://github.com/expressobits/steam-multiplayer-peer)도 구현 참고 후보이며, 최종 엔진 버전과의 호환성은 아직 미검증입니다.

Godot 버전, 내보내기 템플릿 버전, 연동 도구의 출처·버전, Steamworks SDK 요건, Windows 아키텍처, 의존성 라이선스, 두 PC 테스트 결과를 기록합니다. 실제 API 확인 없이 서로 다른 세대의 튜토리얼을 섞지 않습니다.

Steam 판매 자체에 Steamworks API 연동이 필수인 것은 아닙니다. 이 프로젝트는 친구 참가와 통신 경험을 구현하기 위해 연동을 제안합니다. [Steamworks API 개요](https://partner.steamgames.com/doc/sdk/api)

## 3. 플레이어의 참가 흐름

1. Steam에서 실행하고 연동을 초기화합니다.
2. 방장이 비공개 로비를 만들고 친구들이 Steam 초대로 참가합니다.
3. 게임·통신 규약의 버전 호환성과 빈자리를 확인합니다.
4. 모두 준비하면 방장이 근무를 시작합니다.
5. 첫 버전은 근무 도중 새 참가를 막습니다. 나간 사람의 자리는 로비로 돌아온 뒤 채웁니다.
6. 함께 종료한 뒤 파티를 다시 만들지 않고 로비에서 재도전합니다.

참가자가 끊기면 들고 있던 화물을 회수 가능한 상태로 놓고, 남은 팀이 종료하거나 재시작할 수 있게 합니다. 2인 미만이면 설명과 함께 로비로 돌아갑니다. 방장이 나가면 다른 사람은 안내를 받고 메인 메뉴로 돌아갑니다. 방장 이전과 근무 도중 재접속은 나중으로 미루며, 제한을 UI와 테스트 안내에 명시합니다.

## 4. 공유 상태의 담당 구분

| 시스템 | 방장의 책임 | 참가자 화면의 표현 |
| --- | --- | --- |
| 플레이어 이동 | 상호작용 위치의 최종 판정과 제한된 밀림 효과 처리 | 즉각적인 이동 반응과 방장 상태에 따른 보정 |
| 들기 | 화물당 소유자 한 명 결정, 집기 거리 확인 | 안정된 운반 자세, 집기 성공·실패 표시 |
| 던지기·받기 | 놓기·받기 결과 확정 | 조준 미리보기와 부드러운 움직임 |
| 접착 | 유효한 연결 하나와 해제 시점 결정 | 연결 표시, 시간 신호, 명확한 분리 |
| 재채기·점프 | 예고 시점을 맞추고 효과 적용 | 시각적 예고와 각 화면에서 재생하는 효과 |
| 배송 | 제한된 입고, 정상 출고 한 번만 처리, 분실 화물 회수 | 동일한 라벨·진행도·회수 반응 |
| 근무 결과 | 타이머·할당량·성공 상태 관리 | 확정된 팀 결과 표시 |

중요한 상호작용은 안정적인 상태와 제한된 힘으로 처리합니다. 모든 PC에서 강체 물리 계산이 완전히 같아야 하는 구조를 피합니다. 화물 수, 접착 수, 효과 빈도를 제한합니다. 과장된 시각 반응과 단순한 게임 상태를 함께 사용할 수 있습니다.

메시지는 로비 참가 여부, 게임 단계, 물체 존재, 거리, 소유 상태를 확인합니다. 오래되거나 중복된 출고 요청을 거부해, 늦은 패킷이나 동시 행동에도 규칙이 유지되게 합니다.

## 5. 접속 실험

전체 작업장을 만들기 전에 서로 다른 Steam 계정 두 개, PC 두 대, 별도 인터넷 연결에서 파티 생성, 이동, 같은 물체 집기 경쟁, 던지기, 연결 종료, 로비 복귀를 검증합니다. 이후 4인으로 반복합니다.

한 PC의 여러 창 테스트는 개발에는 유용하지만 계정 권한, 초대, 가정용 네트워크 연결, 실제 지연을 검증하지 못합니다.

실제 앱과 적절한 Steam 테스트 권한이 생기면 그것을 사용합니다. 개발 실험용 샘플 App ID는 출시 설정과 분리해야 합니다. 다른 제품의 App ID로 이 게임을 공개·배포하지 않습니다.

## 6. 멀티플레이 테스트 표

아래 항목은 모두 **미실행**입니다. 제안한 시험 조건이며 지원 지연 시간을 보장하는 표가 아닙니다.

| 테스트 | 기대 결과 |
| --- | --- |
| 별도 네트워크의 2인 | 초대·참가·플레이·완료·재시작 성공 |
| 별도 네트워크의 4인 | 출고와 접착 결과가 모두에게 일치 |
| 동시에 집기 | 정확히 한 명만 소유권 획득 |
| 재채기·접착 해제 중 집기 | 복제 물체, 영구 연결, 입력 상태 유실 없음 |
| 동시에 출고 시도 | 할당량이 한 번만 증가 |
| 화물을 든 참가자 이탈 | 화물 회수 가능, 세션 흐름 정상 |
| 방장 이탈·충돌 종료 | 명확한 연결 종료 안내와 다시 시작 가능 |
| 버전 불일치·정원 초과 | 이유가 있는 참가 거부 안내 |
| 시작 시 Steam 사용 불가 | 명확한 오류·재시도, 멈춘 로딩 화면 없음 |
| 모의 왕복 지연(RTT) 50/150/250 ms, 패킷 손실 0/1/2% | 행동 지연, 신호 가독성, 소유 상태 보정, 플레이 가능성을 기록하고 문제 시 설계 수정 |
| 실제 지역 간 세션 | 참가 지역, 관측 지연, 실제 사용성 기록 |
| 근무 반복·로비 재사용 | 화물 수 증가, 남은 접착, 준비 상태 오류 없음 |

프레임 단위의 정확한 입력보다 분명한 예고와 여유 있는 받기 판정을 우선합니다. 실제 온라인 프로토타입을 측정한 뒤 허용 범위를 정합니다.

## 7. Windows 내보내기와 SteamPipe 준비

프로젝트와 실제 App ID가 생긴 뒤 다음을 진행합니다. 디포(depot)는 Steam에 올릴 배포 파일 묶음이며, SteamPipe는 빌드 업로드 체계입니다.

1. 호환되는 Godot·내보내기 템플릿과 맞는 네이티브 의존성을 사용해 Windows 출시용 파일을 만듭니다.
2. 실행 파일, 게임 데이터, Steam 연동 런타임, 외부 구성요소 고지만 담은 배포 폴더를 구성합니다.
3. 에디터 캐시, 소스의 자격 증명, 개인 로그, 개발용 실행 파일, 개발 전용 App ID 덮어쓰기 파일은 제외합니다.
4. Steamworks에서 실제 앱, Windows 디포, 패키지, 실행 파일 시작 옵션을 설정합니다.
5. 실제 ID와 파일 경로로 SteamPipe 빌드·디포 설정을 준비합니다.
6. 권한 있는 계정으로 업로드하고 빌드 ID를 기록해 비공개 테스트 브랜치에 배정합니다.
7. 앱·디포 이용 권한이 있는 테스트 계정으로 Steam 설치 후, 개발 환경 없는 PC에서 실행하고 온라인 근무를 완료합니다.
8. 거의 완성된 후보를 Steam 심사 목록에서 요구하는 브랜치에 배치합니다. 제출 전에 그 후보를 실제 설치해 다시 검증합니다.

공식 안내: [Steam 업로드](https://partner.steamgames.com/doc/sdk/uploading), [빌드와 브랜치](https://partner.steamgames.com/doc/store/application/builds).

Steam API를 쓰는 Windows 빌드에는 필요한 Steam 런타임 DLL이 올바른 위치에 있어야 합니다. 개발용 `steam_appid.txt`는 클라이언트 배포에 포함하지 않습니다. Steam에서 실행하면 앱 식별정보를 전달받습니다. [Steamworks API 개요](https://partner.steamgames.com/doc/sdk/api)

## 8. 출시 후보마다 보관할 증거

소스 버전, 엔진·연동 도구 버전, 내보내기 설정, 생성 시각, Steam 빌드·디포 ID, 브랜치, 테스트 담당자, Windows 버전, 기기 사양, 네트워크 조건, 알려진 문제, 이전 정상 빌드 ID를 기록합니다.

판매할 빌드로 최소 요구 사양을 측정합니다. 에디터에서 돌아간다는 이유로 지원을 판단하지 않습니다. 도전 과제, Cloud, 컨트롤러, Steam Deck 표시, 추가 OS는 각자 구현과 검증이 필요한 선택 기능입니다.

## 9. 작은 범위를 위한 기본안

비공개 파티와 외부 음성 채팅으로 시작합니다. 설정은 로컬에 저장하고 별도 게임 계정은 만들지 않습니다. 지속적인 온라인 성장 정보, 공개 매칭 서버, 실시간 AI 서비스, 유료 데이터베이스, 전용 서버군은 가정하지 않습니다. 테스트에서 구체적인 필요가 확인될 때 다시 검토합니다.
