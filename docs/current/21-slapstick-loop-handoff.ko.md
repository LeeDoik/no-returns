## 목적과 기준

‘돈에 눈이 멀어 감당 못 할 택배를 맡는다’를 직접 플레이로 검증한다. 저가 배송 → 수레 구매 → 고가 재채기 배송 → 정산·재도전이 이어지는 8–12분 실험이다. 시간은 관찰 목표이며 제한 시간이 아니다. 수치는 이 실험의 시작값이며 출시 경제가 아니다.

사용자 선택은 고단가 화물 성장·재투자와 병맛 코미디다. 이 문서의 작은 범위로 개발을 이어가도록 요청했다. [이전 논의](20-player-goals.ko.md)와 코미디 시안 (`../../artifacts/concepts/no-returns-slapstick-v2.png`; retired file)을 참고하되 그림의 거대 보행 화물·스캐너·최종 아트를 구현하지 않는다. Manyfast의 이전 PRD와 충돌하면 이 실험 범위에서는 본 문서를 우선하고 전체 제품 명세 변경과 구분한다.

## 범위

고정 맵 하나, 일반/재채기 화물, 수레 하나, 상점 하나, 목적지 두 곳, 공유 잔액, 정산·재시작만 구현한다. 1인으로 전체 루프를 연결한 뒤 2인 직접 연결 협동을 완성한다. 솔로 완료만으로 협동 재미가 검증됐다고 하지 않는다. 온라인 제품 방향은 유지하되 Steam 초대·로비·매치메이킹·호스트 이전·중도 참가·영구 저장은 이 실험 밖이다.

새 지역 개방, 절차 맵, 추가 장비, 화물 손상·등급 보너스, 전투, 체력·죽음, 강제 할당량, 벌금, 전체 래그돌, 최종 아트는 제외한다. 직원은 임시 도형과 무표정 얼굴, 박스는 얼굴·예고 동작·소리만으로 원인을 읽히게 한다. 승인된 기존 에셋을 쓸 수 있으나 새 아트 제작이 실행 가능한 루프를 막아서는 안 된다.

## 플레이 순서와 경제

| 단계 | 행동과 조건 | 돈과 다음 상태 |
|---|---|---|
| 시작 | 트럭 옆에 일반 상자 두 개, 목표에 수레 가격 표시 | 잔액 0, 수레 60 |
| 기본 배송 | A와 B 목적지에 일반 상자 하나씩 납품 | 각 30, 총 60 |
| 투자 | 트럭 상점에서 수레 구매, 미리 본 고가 주문 해금 | 60 차감, 잔액 0; 수레 즉시 등장 |
| 고가 배송 | 재채기 상자 하나씩 출고; A 다음 B에 배송 | 각 90, 두 건 후 잔액 180 |
| 종료 | 고가 두 건 완료 후 트럭에서 정산 | 총 수입 240, 투자 60, 잔액 180; 재도전/종료 |

다음 고가 상자는 이전 납품 확인 뒤 출고한다. 구매 전에 고가 주문의 단가와 재채기 특성을 보여준다. 구매는 한 번만 가능하며 돈 부족·중복 입력은 차감하지 않는다. 납품은 화물 ID와 목적지가 맞고, 운반 소유권이 해제된 화물이 수령 영역 안에 1초 머물면 한 번만 확정한다. 수레에 실린 경우에도 영역으로 운반해 납품 가능해야 한다. 오배송은 물건을 유지하며 올바른 목적지를 표시한다. 지급 후 화물은 비활성화하고 소유권·고정 연결을 정리한다.

중도 정산은 미완료 건수를 보여주고 종료한다. 그 실행 안에서 확정 수입을 취소하지 않는다. 재시작은 두 플레이어·화물·장비·잔액·타이머를 초기화하는 새 실험이다. 프로세스 종료 뒤 저장은 없다. 메뉴에서 이를 명시한다. 이전 논의의 영구 회사 저장을 구현한 것으로 표현하지 않는다.

## 맵과 선택

트럭을 중심에 두고 A까지 넓은 우회로와 좁은 골목을 연결한다. B는 낮은 턱이 있는 작은 마당으로 둔다. 수레가 양쪽 목적지와 우회로를 실제로 통과해야 한다. 깊은 낙하·미로·긴 왕복을 만들지 않는다. 길 폭과 길이는 실제 수레 크기·회전·운반 속도로 조정한다.

좁은 길은 수레 회전이 까다롭지만 손으로 옮겨 전달할 수 있다. 넓은 길은 안정적이다. 재채기 방향을 동료에게 돌리지 않을지, 내려놓고 피할지, 수레에서 내리고 지름길로 전달할지 선택하게 한다. 고가 상자도 손으로 옮길 수 있게 해 수레가 뒤집혀도 진행을 막지 않는다. 별도 동시 들기 시스템은 만들지 않고 내려놓기·받기로 협동한다.

## 수레와 재채기

수레는 화물 한 개를 운반한다. 손잡이에 접근해 E로 밀기/놓기, 적재 위치에서 E로 싣기/내리기. 상황별 안내로 박스 집기와 충돌하지 않게 한다. 단순 Rigidbody 차체와 제한된 연결 힘을 사용하고 바퀴 서스펜션 시뮬레이션은 제외한다. 적재 화물은 연결로 유지하되 월드 충돌을 유지한다. 수레는 손 운반보다 안정적으로 이동해야 하며 실제 시간 절감은 측정한다. 수레가 재채기를 없애지는 않는다.

재채기는 출고 후 최초 집기 또는 적재 때 활성화된다. 이후 8–12초 간격을 시드로 선택하고 1.2초 얼굴 팽창·들숨 예고 뒤 얼굴 방향으로 한 번 분출한다. 배달 전까지 바닥에 놓아도 진행되며 예고 중 내려놓기로 타이머를 초기화할 수 없다. 출고 대기 및 완료 화물은 반응하지 않는다. 첫 실험은 고정 시드, 재도전은 같은 시드/새 시드를 선택한다.

전방 3m·반각 45도 안의 직원과 동적 화물·수레에 벽 가림 검사를 거쳐 한 번씩 충격을 준다. 대상별 초기 속도 변화 목표는 수평 3m/s·위 1.5m/s이며 Inspector로 조정한다. 직원은 별도 외력 속도를 누적·감쇠하고 월드 충돌을 지킨다. 입력을 완전히 잠그지 않는다. 피격 직원의 손 화물은 놓되 수레 적재 연결은 유지한다. 재채기 자체로 자기를 연속 타격하지 않는다. 과도한 카메라 흔들림과 연쇄 무한 발사는 없다.

바깥으로 떨어지거나 끼인 화물·수레는 트럭에서 복구할 수 있다. 기존 객체를 원위치로 복귀시키고 속도·소유권·연결을 정리하며 지급·계약 상태는 보존한다. 직원 구조는 직원을 복귀시키고 손 화물을 현장에 놓는다. 자동 납품이나 돈 지급은 하지 않는다.

## 협동과 UI

2인 호스트·클라이언트 직접 연결, 게임 시작 전 참가 완료. 호스트가 계약·지갑·구매·물리·재채기 시드·납품을 확정하고 클라이언트는 요청한다. 소유자는 화물당 한 명이다. 동시에 구매해도 한 번만 차감·생성한다. 클라이언트도 구매와 복구 요청을 할 수 있다. 중도 정산·재시작은 호스트가 양쪽에 알리고 확정한다. 클라이언트 이탈 시 소유권을 풀고 호스트 솔로 지속, 호스트 이탈 시 설명 후 메뉴로 돌아간다. 이 실험에서는 재접속 대신 새 실행을 사용한다.

기술 선택은 메인 개발자가 현재 Unity 지원 상태와 기존 환경을 확인해 가장 작은 직접 연결 방식으로 결정·문서화한다. 솔로 물리·지급 규칙을 별도 복제하지 않는다. 네트워크가 막혀도 솔로 실행본은 제공하되 협동 게이트를 미완료로 남긴다.

HUD는 현재 목표, 공유 잔액, 다음 구매 비용, 고가 배송 완료 수, 상호작용 안내만 둔다. 화물은 목적지·단가·재채기 예고를 표시한다. 실제 게임 문구는 영어 원문, 문서에는 한국어 대응을 둔다: `Buy trolley — 60` / 수레 구매 — 60, `Premium delivery — 90` / 고가 배송 — 90, `Wrong address` / 잘못된 목적지, `Delivered +90` / 배송 완료 +90, `Restart clears this run` / 재시작 시 이번 실행 초기화. 거대한 설명 팝업 대신 눈앞의 상자와 목표를 연결한다.

## 현재 코드 근거와 개발 순서

[현재 기준](18-unity-mainline.ko.md), [조작 명세](15-unity-controls.ko.md)를 먼저 읽는다. Unity 프로젝트는 `unity/NoReturns`. 확인된 코드: `Assets/_Project/Runtime/WorkerController.cs`, `CarryMotor.cs`, `CargoBody.cs`, `ThirdPersonCamera.cs`, `CarryHud.cs`; 검사 `Assets/_Project/Editor/CarryLabTests.cs`.

WorkerController는 키보드·마우스를 직접 읽고 수평 속도를 덮어쓰며 R로 모든 화물을 초기화한다. 실험에서는 입력 소유자와 외력 처리, 실험 재시작을 구분해야 한다. CargoBody의 낙하 복구도 납품 상태와 연결해야 한다. 기존 CarryLab 장면과 동작은 유지하고 전체 리팩터링이나 SIDE EFFECTS 복원은 하지 않는다.

새 경로 제안: `Assets/_Project/SlapstickLoop/Scenes/SlapstickLoop.unity`, `Runtime/LoopRules.cs`(단계·지갑·중복 방지), `DeliveryPoint.cs`(수령), `SneezeCargo.cs`(예고·분출), `TrolleyController.cs`(밀기·적재), `LoopHud.cs`, `LoopSession.cs`(참가·권한), `Editor/LoopBuilder.cs`, `Editor/LoopTests.cs`. 모두 아직 존재하지 않는 구현 대상이다. 아래는 개발 순서이며 세부 코드·네트워크 패키지 선정은 메인 작업에서 현행 API에 맞춰 작성한다.

- [ ] A: 별도 장면에 일반 배송 두 건, 지갑, 수레 구매, 고가 두 건, 정산·재시작을 연결한다. 중복 납품·구매와 잔액 순서를 자동 검사한다.
- [ ] B: 수레와 예고·분출·회수 경로를 연결한다. 벽 뒤 피격 없음, 예고 중 내려놓기 악용 없음, 완료 후 발사 없음, 외력이 이동 입력에 지워지지 않음을 검사한다.
- [ ] C: 호스트·클라이언트 소유권과 공유 지급을 연결한다. 동시 집기·구매·납품 요청, 이탈, 재시작 시 잔여 타이머와 객체를 검사한다. 솔로와 2인 결과를 분리한다.
- [ ] D: 기존 CarryLab 회귀와 새 검사를 실행하고 독립 Windows 실행본·조작 안내·실행 항목을 제공한다. 기존 `06_Unity_Play.cmd`는 보존하고 별도 실행 항목을 추가한다. 빌드된 실행본에서 배송→구매→고가 배송→정산을 확인한다.
- [ ] E: 사람 플레이를 관찰하고 아래 판정으로 수정 또는 보류한다. 기획서 수치 변경은 양언어에 함께 기록한다.

기존 회귀 명령: `powershell -NoProfile -File tools/unity.ps1 test`. 문서 검사: `python tools/check_docs.py`. 새 실험 검사는 별도 실행 진입점을 추가하고 정확한 명령·로그·종료 코드를 결과 문서에 남긴다. 기존 검사가 새 경제·협동을 검증한다고 하지 않는다. 변경 파일만 다루고 현재 작업 트리의 다른 변경은 보존한다.

## 재미 검증과 완료 조건

가능하면 서로 다른 2인 팀 두 팀으로 진행한다. 첫 실행은 설명을 최소화하고, 두 번째는 같은 시드로 숙련 효과를 본다. 추가로 새 시드를 선택할 수 있다. 표본이 작아 출시 재미를 증명하는 실험은 아니다.

기록할 것: 첫 구매까지 시간, 건당 이동·회수 시간과 수입, 첫 사고의 원인을 설명하는지, 동료 때문에 계획·역할을 바꾼 사건, 사고 뒤 조작을 회복하는 시간, 플레이어가 자발적으로 다시 하고 싶은 이유. 웃음 횟수만으로 판정하지 않는다.

진행 기준: 팀이 다음 구매 목표를 이해하고, 적어도 한 번 사고를 이해한 뒤 다른 해법으로 수습하고, 구매 효과와 고가 배송의 새 문제를 말할 수 있다. 보류 기준: 예고를 못 읽어 억울하다고 느끼거나, 수레 구매가 체감되지 않거나, 한 명이 계속 대기하거나, 고가 배송이 느린 저가 배송과 같다고 평가한다. 이때 맵·장비를 늘리지 말고 예고·충격·수레·경로를 먼저 조정한다.

자동 규칙 통과, 실제 실행본 완료, 별도 PC 연결, 사람 재미 검증을 각각 보고한다. 사람이나 장비가 없어 미실행인 항목은 남겨두고 실행 가능한 빌드와 관찰 양식을 인계한다. 현재 모든 구현·플레이 항목은 미완료이며 이 문서 작성은 검증 완료가 아니다.
