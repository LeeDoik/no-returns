# 기획 → 구현 → 검토 개발 루프

[English](06-iteration-loop.en.md)

상태: 운영 방식 제안 · 2026-09-09 · 기준 빌드 0.9.3. 이 문서 작성으로 자동 실행·예약 작업이나 출시 승인이 생기지는 않는다.

## 반복 단위

한 반복은 하나의 관찰 가능한 플레이 문제를 해결한다. 기획에서 문제·플레이어 영향·재현 장면·범위 밖·완료 조건을 먼저 적는다. 예: ANI-01의 운반 회전에서 손과 상자의 어긋남. 같은 반복에 맵 확대와 물리 재설계를 끼워 넣지 않는다. 취소된 힘 기반 잡기는 재도입하지 않는다.

구현은 기존 비교 기준과 Git 복구 지점을 확보한 뒤 최소한의 일관된 변경으로 진행한다. 한 실험에서 서로 독립적인 변수를 한꺼번에 바꾸지 않는다. 플레이로 확인할 수 있는 결과를 만든다. 관련 한영 명세·가이드·백로그와 작업 기록을 갱신한다.

검토는 세 층으로 한다: 규칙·충돌·통신 자동 검사, 변경 전후 동일 장면의 실제 연속 플레이/영상 검토, 사람의 조작감·이해도·재미 평가. 검토할 때 기획의 완료 조건을 다시 읽고 이를 반증할 사례를 찾는다. 자동 통과를 재미나 출시 승인으로 바꾸지 않는다.

## 검토 결과와 다음 행동

- 기술 검사 실패: 같은 문제를 수정하고 해당 검사 재실행. 완료 조건을 낮춰 통과시키지 않는다.
- 기술 통과·체감 악화: 개선 완료로 처리하지 않고 수정 또는 되돌리기. 결과를 기록한다.
- 기술 통과·사람 평가 없음: 기술 검증 완료/체감 미검증 상태로 남긴다. 독립적인 다른 작업은 계속할 수 있다.
- 완료 조건 충족: 확인된 범위만 닫고 다음 우선순위로 이동한다. 전체 회귀는 공유 기능 변경·통합 시 수행한다.
- 같은 가설로 두 번 수정했는데 개선 증거가 없으면, 추가 상수 조절 전에 원인과 접근법을 다시 검토한다. 이는 제안한 재검토 기준이며 불가능 판정이 아니다.

## 두 가지 반복 주기

작은 반복은 문제 하나를 다룬다. 작은 반복 3~5회마다 통합 플레이를 진행하는 것을 제안한다. 통합 검토는 실행→참가→계약→보상→다음 계약→종료 전체 흐름을 다루고, 새 그룹의 반응과 누적된 부작용을 확인한다. 횟수보다 위험한 공통 변경이 있으면 즉시 통합 검토한다.

매 단계마다 사용자 승인을 요구하지 않는다. 승인된 범위의 기획·구현·기술 검토·문서화는 이어서 수행한다. 다만 사람의 재미 평가를 대신했다고 주장하지 않으며, 범위 변경·계정 작업·게시/출시 등 별도 승인이 필요한 결정은 구체적인 결과를 준비해 요청한다. 사용자 외 다른 사람에게 연락하거나 테스트를 모집하려면 허가가 필요하다.

## 현재 프로젝트의 순서 제안

2026-09-09 보충: 아래 한 구역 검증과 작은 출시 범위는 이전 운영 제안이며 장기 기획의 크기를 제한하지 않는다. 사용자는 이동·랜덤 맵을 포함한 넓은 확장 탐색을 요청했다. [확장 방향](08-expansion-directions.ko.md)을 검토할 때는 큰 비전에서 검증할 질문을 정한 뒤 실험 범위를 선택한다. 아래 순서가 새 비전 선택보다 우선하는 확정 일정은 아니다.

1. ANI-01: 기존 물리를 유지한 애니메이션/접촉 검토. 좁은 통로의 집기→회전→정지→놓기를 첫 비교 장면으로 삼는다.
2. MAP-01: 맵 전체 확장보다 한 구역의 우회·지름길·동료 도움을 10분 정도의 플레이로 검증한다. 10분은 시험 범위 제안이지 콘텐츠 목표의 확정이 아니다.
3. QA-01/NET-01/PERF-01: 별도 PC·네트워크, 초대, 완주/재시작, 저사양 성능을 검증한다. 구조적 위험은 위 단계와 병행해 일찍 조사한다.
4. ART-01/UX-01: 확정된 플레이를 기준으로 아트·음향·안내의 일관성을 완성한다.
5. REL-01: 계정·앱·상점 준비 상태는 일찍 확인하되, 실제 출시 판단은 [출시 체크리스트](05-validation.ko.md) 근거로 한다.

## 종료 조건

출시는 기능 개수나 완성도 백분율로 결정하지 않는다. 합의된 작은 출시 범위 고정, 실행·진행 차단 문제 해결, 목표 기기의 성능 기준 충족, 실제 외부 협동 검증, 초보자 이해도와 재미 검토, 권리·상점·빌드 심사·지원 준비가 필요하다. 성능 목표와 수용 가능한 미해결 문제는 테스트 전에 명시한다. 현재 이 조건들은 모두 충족된 상태가 아니다.
